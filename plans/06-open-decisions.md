## Agent assumptions
- Code review fixes (agent assumptions, 2026-10-27, from the full-repo review). **Removal is now a two-device flow with an honest limit:** the acting core member copies a removal request to a second core member (over Signal), who authorizes it on their own phone (an HMAC over the request facts, made with the room key), and the first device refuses to remove without that code. The limit, stated plainly: the room key is shared, so a seized device that holds it can make the code itself; the flow makes the process real (two phones, two humans) but is not cryptographic proof the second device acted. Making it cryptographic would need per-device signing keys, which 05-security §Deniable edits rejects because a signed approval is exactly the artifact a boss could use against a member. Read as: process-level two-device approval, deniability intact. **Recovery shares are now room-bound:** each share carries an HMAC (HKDF of the share value, room id as salt and message) that the holder can verify and the app checks before rebuilding, so a share from another room or a tampered one is refused instead of silently rebuilding whatever polynomial the shares came from. **The sync server lost its DELETE route:** deleting a queue was a destroy primitive a stranger could aim at a label without proving membership; the 31-day expiry purge is the path out, and the removal flow relies on expiry plus re-keying rather than a wipe. **The default sync server is the site's own origin:** the app proxies `/mailbox/` and `/match/` from the site host to the sync service (Caddy and traefik configs), because the site's CSP (`connect-src 'self'`) otherwise blocks the browser from talking to `sync.organizeyourworkplace.com` at all — the same-origin proxy keeps the CSP strict and works for self-hosters who host the app too; a self-hoster who wants one app talking to another host's server needs a CSP change on the app's box, documented in the sync-server README. **The dev superuser password only applies to a localhost cms:** a build pointed at a real cms with no PB_PASS now fails loudly instead of trying the dev password against production. **Evidence exports carry their language:** the timeline and the CSV take `lang` and give Spanish labels and Spanish column headers, instead of the dead conditional that shipped English everywhere.
- R3.10 code delivery (agent assumption, 2026-10-27): a release is a manifest of every app file with its SHA-256, signed with an ECDSA P-256 key (the browser's crypto takes the raw r||s form, so the script signs with `ieee-p1363`), and recorded in `transparency/log.jsonl` where each entry carries the hash of the one before it. The log is the index: the app reads it to learn which versions exist, so there is no "latest" pointer that a tampered server could move. The signed releases live in `releases/` in the repo, because the log points at their exact bytes and a rebuild has to reproduce them; the build copies them into the site (`scripts/publish-releases.mjs`). The bytes that get signed are built by one implementation (`src/lib/workspace/canonical.mjs`) that the app and the signing script both use, so the two cannot drift. The phone keeps a known-good copy of the version it is running in a service worker cache (`public/app-sw.js`); the worker only serves files the app checked and hands it, and a file it does not have comes from the network and is not kept, so a tampered server cannot put code in the cache. The worker needs the `Service-Worker-Allowed: /` header to cover `/app/` and `/es/app/` (added to the Caddyfile and the traefik config). The service worker is code too, so it is in the manifest and is checked before it is registered. Still owed: the app on its own subdomain with SRI on every file (A8), which is a deployment change on the box rather than a code change.
- The cms is on PocketHost (owner decision, 2026-10-27): the instance is `oyw.pockethost.io` and the credentials are in `.env.local` as `POCKETBASE_API_URL` and `POCKETBASE_API_TOKEN`. The schema lives in `pb_migrations/1793130359_created_cms_collections.js` (generated with `pocketbase migrate collections` from the local dev instance) and goes up with `phio deploy`; the data goes up with `scripts/cms-seed.mjs`, which matches every collection on its own key (slug+lang for the pages, union_id, sector_id, rule_id, state+topic, type+name+area, employer+union+year, id) so running it twice makes no duplicates. The fetch script reads `POCKETBASE_API_URL` and `POCKETBASE_API_TOKEN` as well as `PB_URL` and `PB_TOKEN`, and reads `.env` and `.env.local`. PocketHost has no backups of its own and no encryption at rest (07-stack-and-hosting.md P1), so the nightly export and the local instance are the backups; only the site's public content goes in it.
- The content pipeline (owner correction, 2026-10-27): the PocketBase `cms` is the system of record and the build reads it. `scripts/cms-fetch.mjs` pulls the pages (as markdown) and the records (as JSON) into `.cache/cms` at build time; `src/content.config.ts` globs the pages from there and `src/data/load.ts` reads the records from there, falling back to the committed `data/*.json` mirror (P4) when there is no cms to read. The prose is no longer committed to the repo. The pages keep their markdown and the same front matter schema, so Astro's own markdown pipeline renders them and the validation is unchanged. `CONTENT_REQUIRED=1` makes the build fail without a cms, for the production build on the box. The CI passes `PB_URL` and `PB_TOKEN` from the repository secrets when they are set, and warns when they are not, so the CI build checks the real content once the owner points it at the cms. The fetch runs as a script rather than through `astro-loader-pocketbase` (installed and pinned, 4.0.8) because the loader hands the body to `render()` as HTML and the cms holds markdown, which would have shown the raw markdown on every page.
- R3.9 the hand off formats (agent assumption, 2026-10-27): the Broadstripes file is CSV, not XLSX, because Broadstripes reads CSV and a hand-written XLSX writer (a zip of XML, no dependency) is not worth the risk before launch. Both files carry a Custom ID that is a random number, never made from the name, so a second export updates the records instead of duplicating them. The notes are off unless the organizer asked for them, and the file says so. The file-setup note goes at the end of the upload file, and the summary is a separate file. The summary sheet holds the counts, the top issues and the conversation count, and no individual note. The two `TODO(verify)` items in the spec (Action Builder's sample file and Broadstripes' full auto-mapping header list) are still open and are a human check before launch.
- R3.9 the sync server image (agent assumption, 2026-10-27): the sync server is one container with one process and one port. It runs the mailbox guard and the matchmaker behind the same origin, because the app has one address for a room and a browser will not talk to two. The queue lives in a SQLite file on a volume (node:sqlite, no dependency to install), with the PocketBase store still available for a host that already runs it; the owner's box compose grows a `sync` service and the proxy grows a `sync.organizeyourworkplace.com` router, while the old `mbx_guard` and `sig` services stay until the owner cuts them over. The server answers cross-origin requests, because the app runs on a different site: the queue label is the capability, the server holds ciphertext only, and the rate limits bound the abuse. `ALLOWED_ORIGINS` lets a host be strict. The client syncs the room document as Yjs updates, sealed under a key derived from the room key; the label is derived from the same room key and rotates every day. The changes that pile up between two posts are merged with `Y.mergeUpdates` before they go out, so a device never receives half a coworker. The sync client is one per page: the workspace session is cached, because two copies of the document in one page would mean the app and the sync client changing different things.
- R3.8 screens 9 to 11 and the join flow (agent assumption, 2026-10-27): the evidence locker keeps each item (date, kind, description, optional file up to 2 MB) inside the encrypted room document, so a photo of a pay stub never reaches a server; the hand off exports a dated plain-text timeline and a CSV using the same columns as the R2 CryptPad wall chart, and the export button stays disarmed until two core members approve and the person doing it is one of them. The join flow runs phone to phone: the invitee opens the link, the app takes the secret out of the address bar, makes a join request, and hands the request over by copy and paste; the inviter approves after the four-word check code is compared out loud and sends the key response back the same way. This is deliberate: the sync server from R3.6 is not wired into the app yet, and the mailbox needs a host and a build-time config. The recovery shares need three core members; with fewer, the app says so instead of making a two-of-two that leaves no margin. Reversible: the wire format for the request and the response is a plain JSON blob, so the mailbox can carry the same payloads later.
- R3.8 the app shell and screens 0–4 (agent assumption, 2026-10-27): the app is a set of static Astro pages under /app and /es/app with client-side TypeScript, no framework, matching how the tools are built. The unlock key lives in sessionStorage for the tab, so a member types the passphrase once, and the app locks itself after five minutes idle or one minute in the background; the workspace on disk stays sealed under the passphrase the whole time. The lock screen and the browser tab carry the disguise name, so the chrome shows no union vocabulary. The bottom nav shows only the sections that exist, so nothing points at a screen that is not built. A "load a sample drive" button on the lock screen fills a labelled sample drive so people can try the app and so the usability sessions have something to look at. Screens 5–11 land next. Reversible: the shell is small, the screens are separate files.
- R3.7 removal, recovery and backups (agent assumption, 2026-10-27): "2 core members" for a removal is read as two core members in total (the one doing it plus one more), which is how the export rule is worded in the same table. A removal re-keys every surviving room, moves each to a new room id derived from its new key, drops the point room of the person removed, and deletes the old mailbox queue by label; the app states plainly that past syncs cannot be taken back. Recovery shares are Shamir over GF(2^521-1) with BigInt, 2-of-3, one share per holder, and the share index travels with the share so any two holders can rebuild the key; the two holders rebuild it once and seal it to the new device rather than keeping a copy. The backup file is a fixed header plus salt, iv and AES-GCM ciphertext under a PBKDF2 passphrase, holding the member's rooms and the keys they hold. The queue delete is authorized by knowing the label, which only members can compute from the room key. Reversible: the backup format can change before launch, the recovery scheme cannot without losing existing shares.

- R3.6 servers (agent assumption, 2026-10-27): three changes to how the spec was written. The matchmaker relays over plain HTTP with a pull loop instead of a websocket, because the rules (proof of work, room cap, join rate limit, no logs) are the security-critical part and an HTTP loop is dependency free and testable end to end; a websocket transport can be swapped in later without touching the rules. The mailbox rules (31-day cap, size cap, per-label rate limit, hourly purge) live in a small guard service in front of PocketBase instead of a PocketBase hook, so they are unit tested in the same language as the rest of the repo; PocketBase is no longer exposed to the internet and the collection rules are superuser-only. The TURN relay is coturn with a config file, no code. Reversible: the guard can move into a PocketBase hook, and the matchmaker transport can change, without touching the client protocol.

- R3.4 keys and invites (agent assumption, 2026-10-27): device keys are ECDH P-256 pairs generated non-extractable in the browser, so a room key can be handed to one new device with no server in the middle. The invite secret is a 32-byte bearer capability that lives only in the link fragment and authenticates the join request (HMAC over the request transcript), so a requester without the link is refused. The 4-word check code is 32 bits taken from a 256-entry HMAC over the session transcript, so both sides derive the same words and a relay cannot. The wordlist carries an English and a Spanish word per entry and the check display puts the index next to the word, because the index is what a pair reading in different languages can compare. The invite screen is deferred to R3.8 (screens 0-11), since there is no app shell yet. Reversible: the protocol surface is small, the UI is not built.

- R3.3 sync transport (agent assumption, 2026-10-27): survey found no off-the-shelf encrypted Yjs server meeting the spec's requirements (E2EE envelopes, one-time prekeys, daily-rotating labels, memory-only matchmaker). Y-Sweet (MIT, Rust) and Hocuspocus (MIT) hold plaintext docs; y/hub is AGPL and needs Redis+Postgres. Staying with y-webrtc P2P + custom thin relay/mailbox on PB per 05-security. Fallback if relay proves fragile: Y-Sweet carrying only ciphertext blobs.
